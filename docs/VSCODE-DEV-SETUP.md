# SystemFabric — VS Code Development and Blocker-Resolution Setup

**Scope:** local development and test infrastructure for SystemFabric 0.5.1. This is not a production deployment guide. Never place production credentials in this workspace.

## Preferred path: VS Code Dev Containers

Prerequisites on the host:

- VS Code with the **Dev Containers** extension.
- Docker Desktop or Docker Engine with the Compose plugin.
- A network connection to the configured npm registry the first time dependencies are installed.

1. Extract or clone this codebase into a dedicated folder.
2. Open that folder in VS Code.
3. Run **Dev Containers: Reopen in Container** from the Command Palette.
4. The container uses Node.js 22.23.4 and starts PostgreSQL plus Memgraph. The first post-create step creates `.env` if absent, installs dependencies, generates `package-lock.json` when it is missing, materializes optional assets, and installs Playwright Chromium.
5. Once the bootstrap terminal completes, run `npm run dev:doctor`.

The first dependency install intentionally uses `npm install` if no lockfile exists. Review the generated `package-lock.json`, commit it, and verify `npm ci` from a clean workspace before treating dependency resolution as reproducible. Subsequent dev-container bootstraps use `npm ci` when a lockfile exists.

If bootstrap stops during dependency resolution, verify that the npm registry is reachable and that no stale proxy environment variables are configured. If the browser download fails, rerun `npm run test:e2e:install` inside the container.

### Windows host troubleshooting

The bootstrap invokes Node and npm without `shell=true`, so installations under paths containing spaces (for example, `C:\Program Files\nodejs`) are handled safely and do not emit Node's `DEP0190` shell-argument warning. If you have an older copy of the dev setup, replace `scripts/bootstrap-dev.js` and `scripts/dev-doctor.js` with the versions from the Windows-bootstrap-fix patch archive, then rerun `npm run dev:bootstrap`.

## Host-based VS Code setup

If you do not use Dev Containers, install Node.js 22.23.4 or newer and Docker Compose. From the repository root:

```bash
npm run dev:setup
docker compose up -d postgres memgraph
npm run dev:bootstrap
npm run dev:doctor
```

The `.env` file generated by `dev:setup` contains **local development-only** defaults. The Compose stack binds development service ports to loopback. Do not reuse its credentials or configuration for a shared or production environment.

## VS Code workflow

Use **Terminal → Run Task** or the Command Palette's **Tasks: Run Task**:

- `SystemFabric: Preflight / blocker report`
- `SystemFabric: Unit and security tests`
- `SystemFabric: Full static and unit check`
- `SystemFabric: LIVE PostgreSQL/Memgraph integration`
- `SystemFabric: Browser and accessibility tests`
- `SystemFabric: Generate readiness evidence`
- `SystemFabric: Assert production release gates`

The **Run and Debug** panel exposes `SystemFabric API` and `Debug current Node test`. Start the API with `npm run dev`; open `http://127.0.0.1:8787/health`, `/admin`, or `/platform` on the host.

## Testing commands

```bash
# Static checks and local unit/security tests
npm run check

# Live integration tests. Fails closed when services are unreachable,
# the dedicated test database is missing, or any integration test is skipped.
npm run test:integration:live

# Browser and editor/accessibility E2E tests
npm run test:e2e

# All above checks; live services must be running
npm run test:all

# Rebuild the current readiness report and evidence snapshot
npm run release:readiness

# Intentionally returns non-zero until all mandatory release gates have evidence
npm run release:assert-ready
```

`test:integration:live` uses `TEST_DATABASE_URL` and refuses to infer a test database from `DATABASE_URL`. The database name must end in `test`. Compose initializes `systemfabric_test` separately from `systemfabric`. The live runner can create a missing test database only when both URLs target the same local host and database user; remote/shared test services must provision the test database explicitly. Run migrations against that disposable database only. Its `integration-live.json` is evidence for this automated subset only; the full `postgres-memgraph-live.json` release gate also requires fresh/upgrade fixtures, outage/rebuild/reconciliation tests, and independent review.

## Optional local integrations

### S3-compatible storage with MinIO

For a host-based workspace, run:

```bash
docker compose --profile cloud up -d minio minio-init
```

For a VS Code Dev Container, add `minio` and `minio-init` to the `runServices` array in `.devcontainer/devcontainer.json`, then rebuild the container so the services join the same Compose network. MinIO console: `http://127.0.0.1:9001` (local-only credentials are in `compose.yaml`). The dev-container environment is preconfigured for the local endpoint and bucket. Use only throwaway fixtures. Run adapter/probe tests and retain output under `artifacts/evidence/`.

### Malware scanner with ClamAV

For a host-based workspace, run:

```bash
docker compose --profile malware up -d clamav
```

For a VS Code Dev Container, add `clamav` to the `runServices` array in `.devcontainer/devcontainer.json`, then rebuild the container so the clamd client and service share a network. The dev container includes the `clamdscan` client configured to connect to the Compose `clamav` service. In the **local `.env` only**, set `LIBRARY_MALWARE_SCANNER=clamdscan`, then restart the API process. Verify clean-file, EICAR test-signature, unavailable-service, timeout, oversized-file, and quarantine behaviors. Do not enable this variable unless the scanner service is actually running; the policy is intentionally fail-closed.

### Third-party identity, email, and billing

OIDC/SAML, real email delivery, and Stripe lifecycle checks require dedicated sandbox credentials and isolated test tenants. Use provider test/sandbox modes, short-lived credentials, least privilege, redacted logs, and never use real customer data. These external checks are not replaced by local mocks or adapter unit tests.

## Operational safety rules

- Keep `.env`, provider keys, credentials, certificates, private keys, customer data, and sensitive artifacts out of Git.
- The Compose volumes contain disposable development data. Do not run `docker compose down -v` unless you intend to delete it.
- The strict integration runner can execute migrations and create test records. Never point its `TEST_DATABASE_URL` at production or a shared database.
- Never convert a missing evidence item into a pass by editing the report manually. Generate evidence from the actual run, record tool versions/environment, and review failures independently.
- A green unit or local integration suite does not equal production certification or WordPress/WooCommerce/BuddyPress/Elementor feature parity.
